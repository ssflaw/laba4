# Exam Service

REST-сервис для проведения экзаменов: преподаватель составляет экзамен из заданий и публикует его, студенты проходят попытки и отвечают на задания, сервис сам проверяет ответы и выставляет итог.

## Сущности

| Сущность | Таблица | Описание |
|---|---|---|
| User | `users` | Пользователь: логин, BCrypt-хеш пароля, роль `STUDENT`/`TEACHER`, статус `ACTIVE`/`BLOCKED` |
| Exam | `exams` | Экзамен: название, проходной балл, лимит времени, статус `DRAFT → PUBLISHED → ARCHIVED` |
| ExamTask | `exam_tasks` | Задание экзамена с эталонным ответом и максимальным баллом |
| ExamAttempt | `exam_attempts` | Попытка студента: `IN_PROGRESS → PASSED / FAILED` |
| TaskSolution | `task_solutions` | Ответ студента на задание в рамках попытки и начисленный балл |

Связи: Exam 1–N ExamTask, Exam 1–N ExamAttempt, User 1–N ExamAttempt, ExamAttempt 1–N TaskSolution, ExamTask 1–N TaskSolution.

## Ограничения целостности в БД

- внешние ключи с `ON DELETE CASCADE`;
- `username` и `email` уникальны;
- баллы и лимиты неотрицательны, статусы только из допустимого набора;
- у попытки `end_time` заполнен тогда и только тогда, когда она завершена;
- у студента не более одной активной попытки на экзамен (частичный уникальный индекс);
- на одно задание в попытке не более одного ответа (`UNIQUE (attempt_id, task_id)`).

## Бизнес-операции

| Операция | Запрос | Правила |
|---|---|---|
| Опубликовать экзамен | `POST /api/exams/{id}/publish` | только из `DRAFT`; есть хотя бы одно задание; проходной балл достижим |
| Архивировать экзамен | `POST /api/exams/{id}/archive` | только из `PUBLISHED`; нет активных попыток |
| Начать попытку | `POST /api/exam-attempts` `{examId, studentId}` | экзамен опубликован; у студента нет активной попытки |
| Ответить на задание | `POST /api/exam-attempts/{id}/answers` `{taskId, answer}` | попытка активна; время не истекло; задание из этого экзамена; повторный ответ заменяет старый; балл считает сервер |
| Завершить попытку | `POST /api/exam-attempts/{id}/finish` | попытка активна; сумма баллов сравнивается с проходным → `PASSED` или `FAILED` |

Дополнительно: экзамен и его задания можно редактировать только в статусе `DRAFT`, решения нельзя менять и удалять после завершения попытки. Операции выполняются в транзакциях с блокировкой строки экзамена или попытки.

## CRUD

`/api/users`, `/api/exams`, `/api/exam-tasks`, `/api/task-solutions` — `GET`, `GET /{id}`, `POST`, `PATCH /{id}`, `DELETE /{id}`.
`/api/exam-attempts` — `GET`, `GET /{id}`, `POST`, `DELETE /{id}`; состояние попытки меняется только бизнес-операциями.

Ошибки: `404` — объект не найден, `400` — нарушено бизнес-правило, `409` — занятый username/email или нарушено ограничение БД.

## Безопасность (JWT)

Аутентификация по JWT с подписью HS256. Серверных HTTP-сессий и cookie нет, поэтому CSRF-токен больше не нужен.
Пароли хранятся в BCrypt.

| Endpoint | Тело запроса | Успех | Ошибки |
|---|---|---|---|
| `POST /auth/login` | `{username, password, deviceId?}` | `200` + пара | `401` неверные данные или пользователь заблокирован, `400` нет поля |
| `POST /auth/register` | `{username, email?, password, deviceId?}` | `201` + пара | `400` валидация, `409` username/email занят |
| `POST /auth/refresh` | `{refreshToken}` | `200` + новая пара | `400` нет поля, `401` токен или сессия недействительны |

Успешный ответ — `{"accessToken": "...", "refreshToken": "..."}`. Access передаётся в заголовке
`Authorization: Bearer <accessToken>`, refresh — только в JSON-теле `/auth/refresh` (access там не нужен).
При регистрации всегда создаётся активный `STUDENT`, `role`/`status` из запроса игнорируются.

**Токены.** Claims: `sub` (username), `jti` (новый UUID при каждой выдаче), `iat`, `exp`, `type` (`access`/`refresh`),
в access ещё `role`. Проверяются подпись, алгоритм HS256, срок, обязательные claims и `type`: фильтр принимает только
`access`, `/auth/refresh` — только `refresh`. Время жизни — `jwt.access-ttl` (15m) и `jwt.refresh-ttl` (7d)
в `application.properties`, секрет — `JWT_SECRET` в `.env` (не короче 32 байт).

**Refresh-сессии** — таблица `user_sessions`, одна строка = одна выданная пара, статус `ACTIVE` / `USED` / `REVOKED`:
- вход и регистрация создают сессию `ACTIVE`; пара возвращается только после её записи в БД, а пользователь
  и его первая сессия создаются в одной транзакции;
- `/auth/refresh` в одной транзакции блокирует строку (`SELECT ... FOR UPDATE`), проверяет владельца (`sub`),
  состояние пользователя, статус `ACTIVE` и `refresh_token_expiry > now`, переводит старую сессию в `USED` и создаёт
  новую `ACTIVE` с тем же `deviceId`. Из двух параллельных обменов одного refresh успешен только один;
- повторное предъявление ещё не истёкшего `USED` refresh переводит сессию в `REVOKED` (это изменение сохраняется)
  и даёт `401`; отозванная сессия тоже даёт `401`;
- ошибка записи новой сессии откатывает всю операцию.

У `DB_USER` на `user_sessions` есть только `SELECT/INSERT/UPDATE`.
Посмотреть статус сессии (TEACHER): `POST /api/sessions/lookup` `{refreshToken}`, токены в ответе не возвращаются.
В БД: `SELECT username, device_id, status, access_token_expiry, refresh_token_expiry FROM user_sessions;`

- `GET /api/auth/me` — текущий пользователь (защищённый endpoint).
- Пользователь со статусом `BLOCKED` не может войти и обновить пару, его ещё действующий access тоже отклоняется.

| Операция | STUDENT | TEACHER |
|---|---|---|
| Просмотр экзаменов и заданий (без эталонных ответов) | ✓ | ✓ |
| CRUD экзаменов и заданий, публикация, архивация | — | ✓ |
| `/api/users` (в т.ч. смена роли и блокировка) | — | ✓ |
| Начать попытку | только за себя | — |
| Ответить, завершить попытку, менять/удалять свои решения | только в своей попытке | — |
| Просмотр попытки/решения | только своих | все |
| Удаление попытки | — | ✓ |

Ответы об ошибках — `{"error": "..."}`: `401` — нет/неверный токен, неверные учётные данные или пользователь
заблокирован (причина не уточняется), `403` — нет прав, `400` — бизнес-правило или нет обязательного поля, `404`,
`409` — занятый username/email или нарушено ограничение БД.

## Запуск

```bash
cp .env.example .env          # задай JWT_SECRET
docker compose down -v   # обязательно после обновления до задания 5 (новая таблица user_sessions)
docker compose up -d
./mvnw spring-boot:run
```

При первом старте контейнер создаёт таблицы (`db/01-schema.sql`), тестовые данные (`db/02-data.sql`) и пользователя `DB_USER` только с правами `SELECT/INSERT/UPDATE/DELETE` (`db/03-app-user.sh`). Приложение подключается под этим пользователем. Чтобы пересоздать БД: `docker compose down -v`.

Сценарий запросов — `requests.http` (IntelliJ IDEA HTTP Client), выполнять сверху вниз на чистой БД.
Блок `J*` — JWT: вход (сессия `ACTIVE`), защищённый endpoint с access, refresh (старая `USED`, новая `ACTIVE`),
повторный refresh (`401`, сессия `REVOKED`), неверные токены и учётные данные; дальше — прежний сценарий на Bearer-токенах.

## Тесты

`./mvnw test` — интеграционные тесты на встроенном PostgreSQL (Docker не нужен): вход, обновление и повторное
использование refresh, ошибки `400/401/409`, параллельный refresh, откат при ошибке записи сессии.
